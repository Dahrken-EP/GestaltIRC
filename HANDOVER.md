# Handover: native media voice on the Linux desktop

Branch `native-media`. Experimental; **do not merge to master** until the
checklist at the bottom is done. `master` does not contain this work.

## What this is

Voice calls for the Linux desktop app that run on a Rust WebRTC stack
(`webrtc-rs`, cpal, opus) inside the Tauri process, instead of the WebView's
own WebRTC — WebView (WebKitGTK) has **no `RTCPeerConnection` at all**
(`getUserMedia` exists, media/peer connections do not). The page keeps its
usual shape: a page-side shim, `web/src/lib/native/pc.ts` (`NativePC`,
`BridgeChannel`), speaks the `RTCPeerConnection` API and forwards to Rust
commands over the Tauri bridge. Everything above (`PeerSession`, voice rooms,
UI) is unchanged; a plain browser path (no `__TAURI__`) is untouched.

## Verified working (2026-10-20)

- In-process selftest: `desktop/src-tauri/src/media.rs::selftest` — two
  connections, DTLS/SCTP both ways, bidirectional Opus mic → RTP → decode →
  mixing. Run: `cd desktop/src-tauri && GESTALT_MEDIA_SELFTEST=1
  timeout 120 ./target/debug/gestalt-desktop` (needs a display; exits 0 on
  pass).
- **Two-instance live check passed**: local bouncer + scripted IRC network,
  two desktop instances in "remote" mode (separate `$HOME`s) logged in as
  `matt`/`jane`, both joined `#chat` and the voice room, drove it with the
  env-gated DOM driver (`GESTALT_MEDIA_LIVE="nick:password"` in
  `desktop/src-tauri/src/main.rs`). Full lifecycle verified: join → ICE
  connected → **RTP/Opus decode both ways** ("the first packet arrived
  (960 samples decoded)" on both), panels show the other person `connected`
  with a working Volume control, mute/unmute, clean leave (teardown, pc
  closed, audio stopped), plus a rejoin that reconnected and decoded again.
- Web: 739 tests pass, `svelte-check` clean. Media commands log each native
  state change (`media: pc N: state connected`), and `log()` timestamps.

## The three bugs the live check caught (all fixed here)

1. **`web/src/lib/native/bridge.ts`** — Tauri 2 keeps `invoke` under
   `__TAURI__.core`, not at the top; the old check silently returned null, the
   whole page fell back to the browser path (no WebRTC in WebKitGTK) and every
   session "could not connect". Now tolerant of both shapes.
2. **`web/src/lib/native/pc.ts`** — `PeerSession` assigns the DOM-style
   property `onconnectionstatechange`; `NativePC` only supported
   `addEventListener` and never fired the property, so the room's peer stayed
   `connecting` and the 45-second safety timer killed every session exactly
   45.000s after connect. Fixed; contract test added in `pc.test.ts`.
3. **`desktop/src-tauri/build.rs` + `capabilities/default.json`** — Tauri 2
   denies app commands to **remote** origins unless the app declares its own
   ACL manifest. `build.rs` names every command via `AppManifest::commands`
   (this auto-generates `allow-*` permissions under
   `desktop/src-tauri/permissions/autogenerated/`), and the capability grants
   them to the window's remote context. Safe: the window only ever navigates
   to the launcher or the address the user named (`on_navigation` allowlist),
   so "loaded at all = allowed to speak".

Note the permission identifiers are hyphenated (`allow-pc-create`, not
`allow-pc_create`) — Tauri rejects underscores in identifiers.

## Rules

- Everything here is experimental: **media must stay out of releases**. Do not
  tag; `0.2.14` shipped from master, which does not have this work.
- The browser path must stay behaviorally unchanged (e2e in Chromium runs it).
- The native path must stay invisible to `PeerSession` consumers.
- Guests in native rooms work (added after review). A guest's connection is marked with `pc_uplink` `guest:<nick>`;
  `mix_for` in media.rs makes the same mixes as the browser's `RoomMixer` (the room hears the microphone and the guests;
  a guest hears the microphone, the room and the other guests, never themselves), unit-tested, and
  `test/native/run.sh guests` checks it against two Chromium pages.

## Automated check (added after review)

`test/native/run.sh` runs the desktop app (debug build, signing in and joining the room by itself) and Chromium in the
same voice room against a real bouncer, and checks both directions of audio, mute, leave and rejoin. It uses
`GESTALT_MEDIA_FAKE_AUDIO=1` — a tone as the microphone, nowhere to play — so it needs no sound server and touches no
real devices; the same variable lets the app run on a machine with no audio. `.github/workflows/native.yml` runs it, and
the selftest, on changes to the native code. Muting was suspected of making the connection flicker to "disconnected";
it does not (that was Chromium closing the page in an earlier manual run).

`BROWSER=firefox test/native/run.sh <scenario>` runs the same scenarios with Playwright's Firefox; all three pass with
both browsers. Safari (and iOS) are not tested: nothing here can run them.

## Running the live check again (by hand, with real devices)

1. Build both sides: `npm --prefix web run build`,
   `cd desktop/src-tauri && cargo build`.
2. E2e stack (see `test/e2e/run.sh` for the pattern): build
   `server` (`go build -tags e2e -o /tmp/.../bouncer ./cmd/bouncer`), run
   `test/e2e/fake_irc.py` on port 16667, run the bouncer on 18080 with
   `web_dir` = `web/dist`, `allow_private_networks: true`; seed users
   `matt`/`jane` with networks pointing at 127.0.0.1:16667.
3. Seed per-instance settings files
   (`"mode":"remote","url":"http://127.0.0.1:18080/"`) under
   `$XDG_CONFIG_HOME/net.gestalt.desktop/settings.json`.
4. Launch two instances with **isolated HOMEs** (`HOME`, `XDG_CONFIG_HOME`,
   `XDG_DATA_HOME`), `DISPLAY=:1`, driver env `GESTALT_MEDIA_LIVE="matt:password"`.
5. **Wipe the WebKit cache after every web rebuild** —
   `$XDG_DATA_HOME/net.gestalt.desktop/WebKitCache` and `CacheStorage` — or
   the window serves the stale bundle and nothing makes sense. This cost us
   an hour.
6. Kill instances with `pkill -x gestalt-desktop` (never `pkill -f`, which
   eats the invoking shell).

Driver behaviour (in `main.rs`, `DRIVER_JS`): pure JS in a Rust raw string —
no TypeScript annotations. It looks at shapes, not words (form ids,
autocomplete attributes, `section.voice`'s own class/button count), so
word changes in any language leave it working. Known quirk: after muting, the
button reads "Unmute", so the driver's unmute step is really a second join-path
click; it rejoins automatically after leaving, which doubles as a teardown/
reconnect check.

## Gotchas worth keeping

- There is no screenshot/click tooling for this rootless Xwayland desktop
  (`DISPLAY=:1`); the driver approach above is the reliable way in.
- A `cargo build` that prints `Finished in 0.1s` did nothing — check the
  binary's mtime against the source before trusting what you launched.
- The 45-second failure is the room's safety timer, not the stack — you will
  find the root cause in page-side state, not in ICE logs.
- `pactl`/`wpctl` per-sink volume control and the drive workflows live in this
  branch only; nothing here is wired into CI.
